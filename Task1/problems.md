# Проблемы и целевая архитектура

На `c4.png` показана предлагаемая архитектура через год после успешного пилота.

Приоритеты указаны по MoSCoW: Must — обязательно, Should — желательно, Won’t — не делаем в первый год.

| Проблема | Как влияет на бизнес | Приоритет | Предлагаемое решение |
|---|---|---|---|
| Отчёты строятся часами | Головной офис поздно получает показатели | Must | Заранее готовить данные для отчётов. Выполнять запросы через Dremio и Power BI отдельно от рабочих БД |
| Новая бизнес-логика попадает в DWH | Развитие финтеха и ИИ зависит от команды хранилища | Must | Перенести новые правила в API соответствующих направлений |
| Медицинские и финансовые данные хранятся вместе | Пользователь может получить лишние данные | Must | Разделить наборы, проверять права в API и SQL-движке, вести аудит |
| SQL Server 2008 и PowerBuilder сложно развивать | Резкая замена может остановить работу клиник | Must | Сохранить старую систему за API. Переносить данные поэтапно и проверять восстановление |
| Новому бизнесу нужны доработки общей шины и DWH | Подключение фармацевтики и электроники занимает больше времени | Should | Использовать API с версиями и согласованные контракты данных |
| Отчётность использует общие ресурсы с рабочими системами | Тяжёлые запросы могут мешать клиникам и банку | Must | Выделить отдельные облачные ресурсы и ограничить тяжёлые запросы |
| О данных знает в основном команда DWH | Сотрудникам трудно найти нужный набор и ответственного | Should | Использовать DataHub: описание, схема, владелец, актуальность и происхождение данных |
| Попытка заменить все интеграции сразу | Работы могут задержать запуск портала | Won’t | Сохранить Camel для старых связей. Заменять только нужные участки |
| Lakehouse ещё не проверен | Можно потратить бюджет без ускорения отчётов | Must | Провести пилот на одном домене. При плохом результате сохранить подготовленные витрины |

Для отчётности каждый домен заранее готовит разрешённые данные. Dremio выполняет запросы, Power BI помогает строить отчёты, DataHub — находить наборы и их владельцев. Права проверяются на сервере с учётом роли и подразделения пользователя.

У клиник, финтеха и ИИ будут свои API, хранилища и команды. Для общих отчётов согласуем значения показателей и ключи организации, периода и продукта.

Медкарты, истории болезни, снимки и результаты исследований остаются в закрытых системах клиник и ИИ. В аналитику передаются только разрешённые поля. Неизвестные поля исключаются из выгрузки. От ИИ нужны только технические показатели: запросы, задержки и ошибки.

SQL Server и PowerBuilder пока продолжают работать. Адаптер передаёт из них утверждённые административные показатели. Новые функции создаются через API доменов.

Для рабочей системы предусмотрим размещение критичных компонентов в разных зонах, резервные копии и проверку восстановления. Размеры ресурсов и требования к скорости уточним на пилоте.

Учебная ВМ из Task4 показывает создание базовой инфраструктуры. Она не рассчитана на хранение сотен терабайт.
